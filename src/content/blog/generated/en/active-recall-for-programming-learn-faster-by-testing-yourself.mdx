Watching a programming tutorial feels like learning right up until you open an empty editor and cannot write the first function. Familiar code feels known even when you could not reproduce a single line of it, and that illusion of understanding is exactly what passive study produces. Active recall for programming closes the gap by forcing you to pull the material out of memory, so the holes show up while you are still studying.

## Where this method comes from

The method combines three ideas that work better together than alone. Active recall means testing yourself by retrieving information from memory instead of rereading it. The Feynman technique asks you to explain a topic as if to a six-year-old, on the logic that if you cannot, you do not yet understand it. The third piece is a coding routine: rebuild code from memory, test it end to end, then re-implement it under different names so you know you learned the idea and not the wording.

## What active recall means and why it works

**Active recall exposes what you think you know but cannot produce.** Suppose you reread a function that sorts a list by age and it looks perfectly clear. Then you open a blank file to write it, and you cannot remember how the comparison works. That gap was there the whole time, hidden until you tried to retrieve the code.

Retrieval also beats recognition and passive review for moving information into long-term memory. Recognition feels like progress because you nod at a correct answer, but nodding never asks you to produce anything. Understanding built through self-testing holds up under pressure, whether that pressure is exam stress or a job interview where you write code on a laptop with no internet access.

## Step 1: Rebuild code from memory, skeleton first

Start with a blank file and rebuild the code in the order below. Working from structure to detail keeps you from getting lost in syntax before you know what the program should do.

1. Write the function signature, loop structure, and return value from memory.
2. Fill in the body, then run the code.
3. Test everything end to end to catch errors such as a wrong implementation.
4. Re-implement the same concept with different function and variable names.
5. Retype or rebuild the material from scratch in any programming language.

### Build the skeleton before the details

A skeleton is the outline of the code: the parts and how they connect. Writing it first shows you what you already know, and the blank spots point to the exact part you need to review. If you can write the loop and the return value but not the condition inside, that condition is your study target for the day.

### Re-implement with new names and a new technique

Memorizing one textbook example proves little, because you may be recalling the wording instead of the idea. Take a Python snippet that reverses a list with slicing, `my_list[::-1]`, and rebuild the reversal with a while loop using names like `items` and `index`. A correct version with different names and a different technique is real evidence that you understand the concept.

## Step 2: Explain it with the Feynman technique

Explain the topic out loud or in writing, as if teaching a six-year-old. Use plain words, and hold off on jargon such as 'closure' or 'idempotent' until you can define each term simply. When you stall, you have found a gap, and that gap tells you more than any feeling of familiarity.

Simplifying a topic for teaching triggers metacognition, which is thinking about your own thinking. That self-reflection improves retention because you have to decide what matters and what can be dropped. Describe a hash map as a set of labeled mailboxes, and the explanation will often expose what you cannot yet say about collisions.

Act as your own annoying questioner. Ask why something works, then why that answer holds, and keep going until you hit a point you cannot answer. For a loop, ask why the stop condition is correct, why the index starts at zero, and what changes when the list is empty. Every question you get stuck on is curiosity pointing you at the next thing to learn.

## Step 3: Close the gaps and recall away from the screen

When you get stuck, go back to the source material and read only the parts you could not explain, then explain the whole topic again from the beginning. Rereading the parts you already know burns time that the gaps need.

1. Note each point where you stalled.
2. Revisit only those parts of the material.
3. Explain the topic again, from the beginning.
4. Step away from your desk and screen, and walk for about half an hour.
5. Try to recall what you were learning, then check the result against your notes.

The walk is a deliberate break from the material. When you come back, recall what you learned without looking at anything, then compare what returns with the actual code. The same loop works for any language or subject, so use it for Python, JavaScript, or SQL alike.

## Writing flashcards that test recall of code

A badly written card lets you recognize an answer instead of producing it, which defeats the point of active recall. The rules below turn the three steps into card design, each one aimed at a specific way cards fail to test recall.

### Ask a specific question, not a label

A front such as 'Slicing a Python list' is a label, and a label lets you recognize the answer without producing it. Write the front as a question instead, such as 'How do you reverse a Python list using slicing?', and put `my_list[::-1]` on the back. The question forces a full retrieval every time the card comes up.

### Keep one concept and one answer per card

Each card should cover a single concept, and each question should have exactly one correct answer. A card that asks how to reverse a list and also how to sort it holds two ideas, so split it into two cards. Otherwise you can get half the card right and still mark the whole thing as known.

### Keep code snippets to 3 to 10 lines

Short snippets are easier to recall in full. Once a snippet runs past 10 lines, the card probably holds more than one idea and should be split. Test yourself by writing the snippet from memory, then compare it line by line with the back of the card.

### Blank the key part with a cloze card

A cloze card hides only the part you need to recall. For a promise chain, write `fetch(url).then(res => ___).then(data => ...)` and recall the hidden part, which is `res.json()`. In Anki, a Cloze note marks the hidden answer with `{{c1::...}}` syntax, as in `The capital of France is {{c1::Paris}}`. A card you answer from memory confirms the recall, and a card you miss shows which part of your code to rebuild next.
